# Questree の使い方

Questree は、AI が開発を進めている間も人間が「現在地」と「次の一手」を見失わないためのタスクツリー。ノードを書き換えるのは AI の仕事で、人間は画面で眺め、候補を承認し、判断に答える。だから **あなたが記録しないと、人間からは何も進んでいないように見える**。

使う口は2つある。どちらも同じデータを読み書きする。

- MCP：`questree_*` のツールが見えていればこちら。
- CLI：ツールがなければ `npx -y questree@<版> <コマンド>`。版は `.mcp.json` に書いてある `questree@1.2.3` に合わせる（クラウドや別の PC でも、そのまま動く）。Questree のリポジトリの中では `pnpm questree <コマンド>`。環境変数 `QUESTREE_ACTOR=ai:<自分の名前>` を付ける。ノードは ID のほか、タイトル（完全一致か、1つに絞れる部分一致）でも指定できる。

一覧の記号：✓完了 ▶作業中 ○着手可 ·待ち !要確認 ‖保留 ×廃止 ?候補（AI には毎回は出さない）

ファイル（`.questree/` の中）を直接編集してはいけない。履歴と整合性チェックが壊れる。

## はじめてのとき

人には「入れて、話しかければ一発で出る」体験をしてもらう。準備はすべて AI がして、人にコマンドを打たせない。

| 状態 | すること |
| --- | --- |
| Questree そのものが PC に入っていない | Questree のリポジトリの `INSTALL.md` の手順で AI が入れる |
| `.questree/` がない | 人が使いたいと言ったら、記録をチームで共有するか自分だけにするかを1問だけ聞き（迷ったら共有）、`questree_setup`（見えていれば）か CLI の `setup`。自分だけなら `private`（CLI は `--private`） |
| `.questree/` はあるのに `questree_*` が見えない | CLI の `setup` をもう一度（足りない登録だけ足し、上書きしない）。人に AI を開きなおしてもらう。それまでは CLI で続ける |

## 画面と、どこで動いているか

画面は人の PC のブラウザで見るもの。`questree_open_ui` が「クラウドで動いている」と返したら、その案内をそのまま人に伝える。クラウドの `127.0.0.1` は人の PC からは開けないので、URL を渡して開いてもらおうとしない。

- クラウドで記録した変更は、コミットして PR に入れる。マージして PC 側で pull するまで、PC の画面には出ない。
- PC 側でも同時に記録していることがある。ノードも履歴もノードごとのファイルなので、別々のノードなら Git でそのまま合わさる。

## 流れ

1. **作業の前に現在地を見る。** `questree_overview`（CLI は `now`）。作業中のもの・判断待ち・次に着手できるものを確かめる。頼まれた作業に当たるノードを探す（なければ `questree_search`、CLI は `search <語>`）。現在地に「前回の記録から〜空いています」と出たら `questree_recap`（CLI は `recap`）を読み、「前回は〜、変わったのは〜、次は〜」と人に3行ほどで伝えてから始める。
2. **取りかかるノードを作業中にする。** `questree_set_status` の `start`（CLI は `start <ID>`）。依存先が終わっていないノードには取りかからない。
3. **必要なだけ広げて読む。** まず概要、次に `questree_node`（深さと含める情報を絞る）、影響範囲を見るときは `questree_neighbors`、経緯は `questree_history`。最初から全部を読まない。
4. **終わったら根拠を添えて完了にする。** `done` の `reason`（CLI は `--reason`。ないと拒否される）に、通ったテスト、PR、コミットなど人間が確かめられるものを書く。`evidence` に `{kind: "pr", ref: "#12"}` や `{kind: "commit", ref: "<ハッシュ>"}` のように参照も付ける（CLI は `--pr`・`--commit`）。根拠のない done はしない。

## ツリーを立体的に育てる

人間はツリー画面で「通ってきた道」と「これから」を眺めて元気をもらう。兄弟が依存なしで縦に並ぶだけの平たいツリーは、どこから来てどこへ向かうのかが見えず、盛り上がらない。ノードを作ったり見直したりするたびに、線を考える。

- 新しいノードを作るときは、**何の上に成り立つか**（先に終わっている必要があるもの、土台にした完了済みのもの）を探し、`depends` を張る。完了済みのノードへの線も張ってよい。「ここから枝分かれした」が線で見える。
- 兄弟を並べたら、順番や土台の関係がないかを見る。並行してよいものだけを並列に残す。
- 大きなまとめ（「MVP の次」など）は、その前のまとめ（「MVP」）に `depends` を張る。左から右へ時間が流れて見える。
- 線が分からないときは無理に張らず、本文に「何の後か」を書いておく。張りすぎて嘘の依存を作らない。
- ノードを作るときは `icon` に**絵文字を1つ**付ける（CLI は `-i 🌳`）。中身が一目で分かるもの（テストなら 🧪、画面なら 🎨、速度なら ⚡）を選ぶ。ツリーを眺める楽しさになるので、付け忘れたノードを見つけたら `update` で足す。
- 取引先や人の名前、公開前の企画など**外に出せない**ノードには `private: true` を付ける（CLI は `--private`）。SNS 共有カードでは名前が「（非公開）」に伏せられる。迷ったら付けておく。

## 途中で起きること

| こんなとき | すること |
| --- | --- |
| 開発の途中から入れた。「これまでの分も入れて」と頼まれた（入れたときに AI から尋ねてもよい） | 下の「途中から入れたとき」 |
| 最初にツリーを組む・計画を書き起こす | `questree_add_many`（CLI は `add --from <ファイル>`）で一度に作る。1件ずつ作らない |
| 作業が大きくて分けたい | 元のノードの下に子ノードを作る（`parent`）か、横に作って `split_from` を付ける。分けた子は正式に作ってよい |
| 頼まれていない課題・思いつきを見つけた | `candidate: true`（CLI は `--candidate`）で候補として残す。正式にするのは人間 |
| 方針が分かれ、自分で決めるべきでない | `questree_ask` で選択肢とおすすめを示す。答えを待つ間、ほかにできることを進める |
| 前提が変わってやめる | `drop`（消さずに残る）。理由を書く |
| 週1レビューのような定期の作業 | `kind: "routine"`（CLI は `-k routine`）のまとめを1つ作り、実施するたびに子「第N回〇〇（YYYY-MM-DD）」を完了で足す。まとめは作業中にしない（いまここにも次に着手できるにも出ない） |
| 進めない（外部待ちなど） | `hold`。理由を書く |
| 「A が終わるまで B はできない」が分かった | `questree_link` で B から A へ `depends`。循環になる線は拒否される |
| 人に「画面を開いて」「ツリーを見せて」と言われた | `questree_open_ui`（CLI は `ui`）。裏で起動してブラウザで開く。人に `serve` などのコマンドを打たせない。開けなかったわけが返ってきたら、それを伝える |
| Questree 自体がおかしい（エラーになる、画面が出ない） | `questree logs --errors`（ノードに絞るなら `--node <ID>`）でデバッグログを読む。`QUESTREE_LOG=debug` を付けて再現すると、引数を切らずに返した値も残る |
| 全部のプロジェクトをまとめて見たい・人生ビューと言われた | `questree_open_life`（CLI は `life`）。ほかのプロジェクトの中身を読みに行かない |
| タスクバーに常駐させたい・アイコンから開きたいと言われた | `questree_tray`（CLI は `tray`）。サインインしたときにも出すなら `autostart: true` |
| 画面のフォントを変えたいと言われた | `questree_fonts`（CLI は `font`）に PC に入っているフォントの名前を渡す。同梱はしない |
| 間違えて書いた | `questree_history` でイベントID（e…）を探し `questree_undo` |

## 途中から入れたとき

導入した日に全部起きたように見せない。過去の記録から、作った・始めた・終わった時刻を実際に起きた頃に合わせる。

1. `questree_past`（CLI は `past`）で、Git の本線のコミット（PR 番号つき）・タグと、このフォルダでの過去の会話（題と時刻）を読む。足りなければ CHANGELOG や日付入りの文書、会話のファイルを手元で読む。会話の全文は `.questree/` に写さない。
2. 機能ごとの塊にまとめてツリーを組み、`questree_add_many` で **`candidate: true`** を付けて作る。各ノードに `past` を付ける：`created`・`started`・`done`（分かるものだけ、ISO 8601）、`source`（`git` / `chat` / `doc` / `inferred`）、`refs`（`abc1234`・`PR #12`・会話のファイル）、幅のある推定なら `approx: true`。終わったものには `reason` も書く。
3. 人に「画面で候補を確かめて承認して」と伝える。承認されるまで達成率と完遂の目安には入らない。推定の日時は画面で ≈ が付く。

```yaml
- title: ログイン画面
  icon: 🔐
  candidate: true
  reason: "PR #3 をマージ"
  past: { created: "2026-10-01T10:00:00+09:00", done: "2026-10-03T18:00:00+09:00", source: git, refs: ["PR #3"] }
```

## してはいけないこと

- 候補の承認（promote）と、判断への回答（answer）。これは人間がする。MCP にはそもそも出ていない。CLI でもしない。
- 根拠のない done。
- `.questree/` のファイルを直接書き換えること。

## 書き方

- タイトルは短く、何をするかが分かる名詞句に（「ログイン画面」「CSV の書き出し」）。
- 本文には、なぜやるか・終わりの条件を1〜3行で。
- 関連するファイルがあれば `files` に（`{path: "src/auth.ts", lines: "10-80"}`）。人間が画面から開ける。
- `reason` は人間が後で読む。「何をして、どう確かめたか」を1文で。
